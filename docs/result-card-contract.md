# 공통 결과카드 계약 · 1.1

세 사업의 정확한 이름과 교안이 확정되기 전에도 공통으로 사용할 수 있는 최소 결과 형식입니다. 결과카드는 학생의 화려한 설명보다 **무엇을 했는지, 어떤 근거로 확인했는지, 다음에 무엇을 바꿀지**를 남기는 데 목적이 있습니다.

## 필수 필드

| 필드 | 의미 | 입력 원칙 |
|---|---|---|
| `programId` / `programVersion` | 어떤 프로그램의 어느 버전에서 만든 결과인지 구분 | manifest에서 자동 입력 |
| `teamCode` | 학생 실명 대신 사용하는 수업용 식별자 | 영문 대문자·숫자·하이픈 2~20자 |
| `completedAt` | 결과카드를 저장한 시각 | 브라우저에서 자동 입력 |
| `summary` | 팀이 만든 결과 또는 내린 결정 | 300자 이내, 한 문장부터 시작 |
| `evidence` | 비교·테스트·관찰·체크리스트 등 검증 근거 | 최소 1개, 근거 이름과 내용으로 구성 |
| `nextStep` | 한 번 더 개선한다면 바꿀 한 가지 | 300자 이내 |
| `aiDisclosure` | 생성형 AI 사용 여부와 실제 사용 범위 | 사용했다면 구체적인 설명 필수 |
| `privacyChecked` | 직접식별정보와 비밀정보가 없다는 팀의 최종 확인 | 반드시 `true` |

## AI 사용 상태

- `not-used`: 결과를 만드는 과정에서 생성형 AI를 사용하지 않았습니다.
- `used`: 생성형 AI를 사용했으며 `note`에 사용 범위와 학생의 재검증 행동을 적습니다.
- `not-applicable`: 프로그램 성격상 AI 사용 여부를 묻는 것이 적절하지 않습니다.

단순한 자동 계산, 검색, 규칙 기반 분류를 생성형 AI라고 표현하지 않습니다. 공개 데모 자체도 생성형 AI를 호출하지 않습니다.

## 개인정보와 비밀정보

결과카드에는 실명, 학번, 학교명, 연락처, 얼굴, 음성, 계정, 참여코드, API 키를 넣지 않습니다. 브라우저 검사는 이메일·전화번호·인증 토큰처럼 형태가 뚜렷한 값만 탐지합니다. 자동 검사는 사람의 최종 확인을 대신하지 않습니다.

공개 클라이언트의 검증 결과는 신뢰할 수 있는 보안 증거가 아닙니다. 향후 `gom-clean`이 결과를 받게 되더라도 서버에서 같은 계약과 개인정보 규칙을 다시 검증해야 합니다.

## 합성 예시

```json
{
  "schemaVersion": "1.1",
  "programId": "program-01",
  "programVersion": "0.2.0",
  "teamCode": "A-01",
  "completedAt": "2026-08-10T10:00:00.000Z",
  "summary": "합성데이터를 사용해 두 가지 설계를 비교했습니다.",
  "evidence": [
    {
      "label": "비교 결과",
      "value": "두 번째 설계가 정해진 확인 항목 세 개를 모두 충족했습니다."
    }
  ],
  "nextStep": "다른 합성 사례에서도 같은 결과가 나오는지 확인합니다.",
  "aiDisclosure": {
    "status": "not-used",
    "note": ""
  },
  "privacyChecked": true
}
```

이 예시는 실제 학생이나 학교에서 가져오지 않은 합성 내용입니다.
