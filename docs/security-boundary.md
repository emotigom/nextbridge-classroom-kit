# Security Boundary

## 공개 영역

- 합성데이터
- 확정된 프로그램 제목·설명·차시·완료조건
- 독립 실행 코드
- 결과카드 JSON Schema
- `gom-clean`과 통신할 공개 계약
- 화면 예시와 강사·학교 IT 안내

확정되지 않은 사업명, 학교급, 수업시간, 팀구성은 실제 값처럼 공개하지 않고 `program-01~03`과 `unconfirmed` 상태로 둡니다.

## 비공개 영역

- 실제 학교·학생·강사 계정
- 수업 참여코드와 세션 토큰
- 학생 제출물 원본
- Supabase 서비스 롤 키
- OpenAI·프록시·Cloudflare 자격증명
- R2/KV/Durable Objects 운영 식별자
- 내부 진단·감사 로그
- 비공개 `gom-clean` 소스코드

## 금지되는 연결

- 공개 저장소가 비공개 저장소를 Git submodule로 참조
- 공개 GitHub Actions가 비공개 저장소를 checkout
- 브라우저에서 서비스 롤 키 사용
- 공개 클라이언트에서 민감 테이블 직접 쓰기
- URL에 장기 토큰 포함
- 실제 학생 데이터로 데모·테스트 수행

## 클라이언트 검사의 한계

공개 데모는 이메일, 전화번호, 주민등록번호, API 키, 인증 토큰처럼 형태가 뚜렷한 값을 기본 차단합니다. 이 검사는 학생의 실수를 줄이는 수업 편의 기능일 뿐 보안 경계가 아닙니다.

- 실명과 학교명처럼 형태만으로 판단하기 어려운 정보는 자동으로 완전히 찾을 수 없습니다.
- 공개 클라이언트의 코드는 사용자가 바꿀 수 있습니다.
- 개인정보 확인 체크박스만으로 안전한 제출이 되지는 않습니다.
- 향후 서버 연결이 생기면 서버가 모든 필드와 금지정보를 다시 검사해야 합니다.

## 서버가 반드시 확인할 것

- 토큰 만료와 프로그램·세션 범위
- 요청 본문 스키마와 최대 길이
- 팀코드 형식
- 허용된 파일 형식과 최대 용량
- 속도 제한과 중복 제출
- 개인정보·금지 콘텐츠 차단 흐름
- 제출 및 삭제 책임의 기록

## 공개 자동화 원칙

비공개 저장소에서 공개 저장소로 자료를 보낼 필요가 생겨도, 공개 워크플로가 비공개 코드를 읽게 하지 않습니다. 비공개 측에서 허용 목록에 포함된 생성물만 검사한 뒤 공개 저장소에 PR을 만드는 단방향 구조를 사용합니다.
